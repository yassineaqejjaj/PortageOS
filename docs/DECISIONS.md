# Décisions
- D-001 (2026-11-08) Démarrage sans design : tokens appliqués plus tard ; aucune UI finalisée avant import.
- D-002 pnpm workspaces, TypeScript strict, vitest.
- D-003 Décimales via decimal.js ; TVA arrondie par ligne (à valider).
- D-004 Hébergement : Vercel/Railway par défaut ; alternative UE (ex. Scaleway/OVH) à documenter avant données réelles RH/paie.
- D-005 Git local sur `main`, pas de remote.
- D-006 (2026-11-08) Design importé depuis l'artifact Claude Design (portage.css). Navigation limitée aux routes réelles ; pas d'écran du design branché sur des données fictives. Polices via next/font (RGPD).
- D-007 (2026-11-09) Polices auto-hébergées via @fontsource (et non next/font/google) : `next/font/google` télécharge les polices pendant le build et a fait échouer des builds (CI et Vercel) de façon intermittente ; fontsource est déterministe, hors ligne et sans appel à Google.
- D-008 (2026-11-09) CRM : le scoring est un barème **transparent** (points justifiés, pondérations par société, bornes 0-100), jamais un modèle opaque ni une décision automatisée ; la règle d'une commission est **figée** à la création du parrainage (trigger) et un montant payé ne change plus ; une commission est approuvée par une autre personne que celle qui l'a générée ; la simulation commerciale n'utilise qu'un taux de frais approuvé ou saisi comme hypothèse et ne calcule ni cotisations ni net salarié ; un accord-cadre actif plafonne le TJM des missions rattachées. Les commissions sont comptabilisées 622/512 sans prétention fiscale (à valider par l'expert-comptable).
- D-009 (2026-11-09) Clients : le délai de paiement est une donnée convenue, jamais une règle légale appliquée ; la consommation d'un bon de commande est calculée (jamais saisie) à partir des factures émises et son dépassement est signalé sans bloquer la facturation (décision métier à confirmer) ; la somme de contrôle du SIREN est un avertissement car Sirene n'est pas connecté.
- D-010 (2026-11-09) Banque : aucune connexion bancaire ; import CSV seulement. Un rapprochement n'est jamais automatique (même avec référence exacte) car il crée une écriture comptable ; les propositions ambiguës (plusieurs factures de même solde) ne sont pas proposées. Les débits sont écartés du rapprochement des encaissements.
- D-011 (2026-11-09) E-mail : le journal de livraison ne conserve ni corps ni lien ni adresse en clair ; sans `SMTP_URL`, `not_connected` est écrit et l'administrateur reste le recours pour les réinitialisations.
- D-012 (2026-11-09) Facturation : les totaux d'une facture sont toujours la somme de ses lignes (jamais saisis) ; TVA par ligne avec taux saisi ; lignes figées dès l'émission (trigger) ; le PDF est un document de travail tant qu'aucune plateforme agréée n'est connectée et que les mentions du vendeur ne sont pas complètes. Avoirs partiels et acomptes non faits : ils modifient le solde exigible et l'écriture comptable, à concevoir avec un expert-comptable.
- D-013 (2026-11-09) CRA : l'unité est portée par la mission (`day`, `hour`, `forfait_jours`). Pour une mission horaire, la colonne historique `dailyRate` contient le tarif **horaire** et la facture est libellée en heures ; les accords-cadres (plafonds journaliers) sont refusés pour ces missions. Aucune règle légale n'est codée : le plafond annuel du forfait jours est saisi par l'administrateur, affiché à titre informatif et jamais bloquant ; le suivi de charge et de repos du forfait n'est pas modélisé. Les relances sont des notifications internes déclenchées manuellement (une par mission, mois et jour, contrainte unique en base).
- D-014 (2026-11-09) Missions : un avenant est append-only (trigger), motivé et journalisé ; le tarif initial n'est jamais écrasé : le tarif facturé d'un CRA est celui du dernier avenant dont le mois d'effet est ≤ la période du CRA. Un avenant de tarif est refusé s'il touche une période déjà facturée et respecte le plafond de l'accord-cadre. Le budget est un suivi informatif (factures HT non annulées), jamais bloquant. Les prévisions de pilotage utilisent encore le tarif initial (limite connue).
- D-015 (2026-11-09) Console plateforme : l'exploitant est un administrateur du tenant plateforme (`Tenant.isPlatform`), jamais un rôle invitable (la liste des rôles n'en contient pas, donc un administrateur de société ne peut pas se l'attribuer). `isPlatform` est unique (index partiel), immuable (trigger) et exclu des droits du rôle applicatif ; le tenant plateforme se crée hors API (`BOOTSTRAP_PLATFORM=1`) avec MFA obligatoire. La console ne lit aucune donnée métier : métadonnées seulement, chaque action est tracée chez la société visée et chez la plateforme. L'offre est un libellé indicatif ; aucune facturation d'abonnement n'est connectée.
- D-016 (2026-11-11) WhatsApp : fournisseur unique pour ce lot = Meta WhatsApp Cloud API, derrière une interface (`WaProvider`) ; le faux fournisseur n'existe que hors production et marque les messages « simulated » (jamais « sent »). Un canal n'est « vérifié » qu'après un appel réel réussi. Le jeton d'accès est chiffré (même clé que le MFA) et jamais renvoyé ; le secret d'application et le jeton de vérification du webhook sont des variables d'environnement de la plateforme (une application Meta pour tous les tenants ; secret par société non géré). Le webhook est public mais authentifié par HMAC-SHA256 du corps brut (comparaison à temps constant) ; le tenant est retrouvé par `WhatsappRoute` (phone_number_id → tenant, seule table sans RLS, sans secret). Messages entrants et statuts sont idempotents (identifiant fournisseur unique par tenant) ; un statut ne recule jamais. Consentement obligatoire avant tout envoi (preuve et origine, trace d'audit) ; le mot STOP le retire automatiquement ; le rétablir exige une action humaine tracée. Texte libre uniquement dans les 24 h après le dernier message entrant ; au-delà, modèle déclaré par la société (nom Meta non vérifiable par le produit) et activé pour l'envoi automatique. L'envoi se fait après validation de la transaction (message « en file » puis envoi) ; sans tâche de fond durable, les messages restés « en file » se relancent à la main. Corps des messages stockés dans le tenant : pas encore de purge (limite connue).
- D-017 (2026-11-11) Démo pilote BG Consulting : jeu de données injecté **par l'API** (pas par SQL) pour que machines d'état, numérotation, journal et audit restent ceux du produit ; seule la création du tenant et des comptes passe par la base. WhatsApp = faux fournisseur local ; agents = playbooks déterministes. Voir docs/DEMO_BG_CONSULTING.md.
- D-018 (2026-11-11) Simulation de salaire BG : formules rétro-conçues de 6 feuilles de référence et verrouillées par des tests au centime ; **aucun taux en dur** (paramètres datés approuvés à quatre yeux, une clé par tranche de PAS) ; chaque scénario arbitre brut et frais/jour ; le PDF reprend la mise en page de la feuille et n'expose jamais l'enveloppe interne. Envoi WhatsApp : PDF régénéré à l'envoi, document libre dans la fenêtre de 24 h sinon modèle à en-tête document ; sujet de consentement « prospect » ajouté (contraintes SQL étendues) ; le modèle PDF ne passe pas par `send-template`. Estimation non validée juridiquement.
- D-019 (2026-11-11) Simulateur : ajout du taux de rentabilité INTERNE (marge après charges patronales ÷ CA = TJM × jours/an), jamais transmis au destinataire ni dans le PDF ; charges patronales = paramètre approuvé (45 % choisi par la direction, hypothèse non validée), absent = rentabilité masquée. Simplification de l'écran : 3 champs obligatoires, résultat en direct via un aperçu serveur non enregistré (`POST /crm/salary-simulations/preview`, aucun calcul dans le navigateur), enregistrement automatique au PDF/envoi, réglages avancés repliés.
